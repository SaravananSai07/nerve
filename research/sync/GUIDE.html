nerve sync guide

Follow, steer and move Claude Code sessions across your Mac, Pi and phone. This page covers how it works and what crosses the wire, what was measured, what's still untested, and how to try it on each device.

Where it stands (round 2, 2026-10-12)
  • One command per device. nerve setup on the first device prints a code. nerve setup <code> on each other device does everything else: identity, relays, the Claude mod, a background service, and pairing in both directions. Joining took 4–7 s (E17, E23).
  • Claude Code mods are in. A small mod runs inside each Claude session. It does three things:
    • submits prompts from other devices, queued safely if Claude is busy;
    • answers permission prompts and questions from anywhere, while the dialog stays on screen locally;
    • reports each turn as it finishes.
    Questions no longer need "away mode". Terminal paste and settings hooks remain as fallbacks.
  • Hand-offs are incremental. Only commits the target lacks, plus content-addressed chunks of everything else.
    • First hand-off: 694 KiB.
    • The same session one turn and one commit later: 16–19 KiB.
  • The Devices view was rebuilt. Two panes on a laptop, tabs on a phone-sized terminal, with "needs you" first.
  • Tested: one-Mac runs (E17–E22) and Mac ⇄ Pi over public relays only (E23–E26, E25b), plus 223 unit tests. Clippy is clean.
  • Still missing: a native phone app; iPhone remains SSH-only.

1. Setting up a device

On the first device (say your Mac):

./install.sh --sync          # from the repo: builds nerve with sync, then runs `nerve setup`
# or, with nerve already built:  nerve setup

It prints a block like this, then waits for another device to join:

nerve setup
  ✓ created device 'mac' (npub1dc6d7h0…cmuflx), relays: wss://relay.primal.net wss://relay.snort.social
  ✓ nerve mod installed for Claude Code 2.1.295 (new sessions load it)
  ✓ background agent runs at login (launchd dev.nerve.sync; log …/sync/agent.log)

Add another device: on it, run

    nerve setup nerve1eyJ2IjoxLCJuIjoibWFjIi…

[QR code of the same text]
The code works once, for the next hour. Anyone holding it can pair a device, so treat it like a password.

On every other device:

./install.sh nerve1eyJ2IjoxLCJuIjoibWFjIi…      # or: nerve setup nerve1eyJ2…
  ✓ created device 'pi' (npub1hrdrlnv…a3s8km), relays: wss://relay.primal.net wss://relay.snort.social
  … asking mac to pair back
  ✓ paired with mac: mac now trusts 'pi'
  ✓ background agent runs as systemd user service nerve-sync (also while logged out)

Each step, and what it does:

IdentityCreates a secp256k1 key (<config>/sync/device.key, mode 0600) and fleet.toml. The default relays are the two that reliably delivered for brand-new keys in testing. Joining adopts the inviter's relays, including a private one.
ClaudeOn Claude Code ≥ 2.1.287, installs the nerve mod as a local plugin (claude plugin install nerve@nerve-local), loaded by new sessions. On older Claude, writes settings hooks instead and tells you how to enable them.
Background agentThe service depends on the OS:
  • macOS: a launchd LaunchAgent.
  • Linux: a systemd user unit, plus loginctl enable-linger so a headless Pi keeps it after you log out.
  • Termux and containers: a detached process, plus a Termux:Boot script.
PairingThe joiner trusts the inviter's key, then proves the invite's one-time secret. The inviter's agent trusts the joiner back and acks. A used or expired code gets a clear refusal.

Re-running nerve setup is safe: every step checks what's already in place. To check a device later, run nerve sync doctor. It reports the agent, the mod socket, the mod install, every relay, and every peer's freshness, one line each with what to do about a failure. To add a third device, run nerve sync invite for a fresh code.

2. How it fits together

Mac Raspberry Pi ┌────────────────────────────────────┐ ┌────────────────────────────────────┐ │ claude ──[nerve mod]──┐ │ │ claude ──[nerve mod]──┐ │ │ claude (no mod: tmux paste/hooks) │ │ claude --bg (mod only)│ │ │ ▼ unix socket│ │ ▼ │ │ nerve sync agent (launchd) │ │ nerve sync agent (systemd) │ │ · scans sessions every 3 s │ │ │ │ · chunk store · activity log │ │ │ │ nerve TUI → D (reads the agent) │ │ │ └──────────────┬─────────────────────┘ └──────────────┬─────────────────────┘ │ NIP-44 encrypted, signed Nostr events │ ▼ ▼ ┌───────────────────────────────────────────────────────────────────────┐ │ relays: wss://relay.primal.net, wss://relay.snort.social (public) │ │ ws://<pi-tailscale-ip>:7777 (optional private, nerve sync serve-relay) │ └───────────────────────────────────────────────────────────────────────┘ ▲ phone: SSH (Tailscale) into the Pi → `nerve` → D Android: Termux can also be a device

Every device runs one agent. It does four things:

  • Publishes a snapshot of its sessions to each paired device whenever something changes, and at least once a minute.
  • Receives commands from paired devices and carries them out: send text, answer, fetch, hand off, run a job.
  • Hosts the mod socket, so Claude sessions on the same machine can reach it.
  • Acks every command end to end. A relay saying "OK" is not proof of delivery: two public relays were measured accepting and then dropping everything.

The TUI and the nerve sync … commands talk to the agent through a spool directory, and follow its activity log until the ack arrives.

3. Claude Code mods: what changed

Mods shipped in Claude Code 2.1.287. A mod is a plugin whose JavaScript runs inside the Claude process and hooks its events. That means it can do things nerve could only approximate from outside before. The full API lives in the type declarations Claude writes into a mod's .claude-plugin/types/ on first load: 16,000 lines, read for this round.

Answer a permissionSettings hook nerve sync hook + file mailboxclassic.PermissionRequest hook ⇄ agent socketSame race with the local dialog, but no shell process per prompt, and the request is withdrawn reliably when answered locally (E21).
Answer a questionOnly in away mode, because the hook hid the dialogRaces Claude's own AskUserQuestion dialogThe dialog stays on screen locally. Answer it there or from any device (E20).
ProgressInferred from the transcript every 3 sturn.start / turn.complete with duration and tokensExact turn timing and token use per session, shown in the Devices view.
Status in Claudenone$.ui.status: ⚠ nerve: ⇄ nerve · pi 4s · 1 waiting on another deviceYou can see sync is live from inside the session.
How the mod talks to the agent (protocol)

HTTP/1.1 over a Unix socket (<sync>/agent.sock, mode 0600) via $.http.fetch(url, {socketPath}). No TCP port is opened. Routes:

CallPurpose
POST /v1/helloSession id, cwd and surface (terminal/desktop) on start.
GET /v1/pollLong-poll (8 s) for prompts from other devices; also carries the status line.
POST /v1/request"This permission or question is pending", with Claude's tool input.
GET /v1/waitLong-poll (2 s) for the remote answer to one request.
POST /v1/resolved"Answered here", so the request is withdrawn everywhere.
POST /v1/eventTurn start and turn complete, with usage.
POST /v1/ackOutcome of a submitted prompt; becomes the end-to-end ack to the sender.
Two traps found by testing, and how they're handled
  1. A mod hook has 10 s of its own time.
    • The first version waited for remote answers in a $.clock.sleep loop. Claude cut the hook off at 10 s, and the request vanished from other devices.
    • Time spent inside another $ call doesn't count against the budget. So the hook now waits inside $.http.fetch against /v1/wait.
    • E19 deliberately answers 20 s after the prompt appears.
  2. Claude doesn't abort the hook when you answer at the keyboard.
    • next.signal.aborted stayed false for 14 s after "Yes" was pressed.
    • The mod now also wraps every tool.call. When the same tool call with the same input settles, the request is withdrawn.
    • The agent also drops any request whose hook stops polling for 6 s.

Also found: returning early from tool.call while Claude's permission dialog is open leaves the dialog stuck, and $.ui.ask can't be cancelled. So the mod answers through Claude's own hooks rather than drawing its own dialogs.

Limits of mods:

  • They need Claude Code 2.1.287 or newer.
  • They aren't sandboxed: the nerve mod can approve tool calls, which is its job.
  • They load only in folders you've trusted.
  • A session started before nerve setup doesn't have the mod until it's restarted. The Devices view shows tty or view for such sessions, and the old paths still work for them.

4. Each feature: how, what's sent, trade-offs

Progress and "last synced"

HowThe agent scans sessions every 3 s, using the same discovery as the TUI. On a change, or every 60 s, it publishes a state event per peer. That's an addressable Nostr event (kind 30078), so relays keep only the newest copy. A sleeping laptop therefore still shows what it was doing, and since when.
Sends
  • Device: name, OS, architecture, capabilities, away flag.
  • Per session: id, name, folder, branch, state, what it waits for, cost, subagent count, the last 8 transcript lines, via_mod, and the last turn (time, duration, tokens, model).
  • Also: pending prompts and job status.
Typically 2–10 KB.
UpsideWorks across offline periods and needs no polling. Mod sessions add exact turn timing.
DownsideA snapshot: about 3 s stale at best on the private relay, plus 0.5–1 s on public ones. The tail is a peek; l fetches 200 lines.

Tested: ✓ E10b, E14, E23 (Pi seen from the Mac over public relays only).

Send an instruction

How
  • Mod sessions: the agent queues the text, the mod calls $.prompt.submit, and the mod's ack goes back to the sender.
  • Others: the agent re-checks the PID is still claude, then pastes into its tmux pane or Ghostty tab and presses Enter.
SendsSession id plus the text, control characters stripped, up to 16,000 characters.
UpsideMod path: queued if busy, works in background sessions, and the ack means Claude actually took it.
DownsideDesktop-app sessions without the mod are view-only. Instructions older than 5 minutes are refused rather than typed, so a stale replay can't fire.

Tested: ✓ mod path: ack in 0.37 s on one Mac (E18), 4.8 s Mac→Pi over public relays (E24), queued in order (E18b). ✓ tmux path (E10a). ◐ Ghostty path: the mechanism works (E9), but it was never run end to end.

Answer permission prompts and questions

HowThe mod reports the prompt and waits. Claude's own dialog stays on screen. The first answer wins:
  • Remote: from another device, via the agent.
  • Local: at the keyboard, which withdraws the request everywhere.
Sessions without the mod use the settings hook as before, where questions still need away mode.
SendsThe tool name plus a one-line summary (command, file path or URL), or the question with up to 9 options. Back comes allow, deny or the chosen label.
UpsideAnswer from any device without taking the prompt away from whoever is at the keyboard.
DownsideWaits up to 10 minutes for permissions and 30 for questions, then falls back to local only. Multi-select questions answer only the first option set.

Tested: ✓ permission held for 20 s, then answered remotely (E19); question without away mode (E20); local answer withdrawn (E21); across machines over public relays (E25b: visible on the other device after 6 s, file written after the answer).

Read changes, transcript and subagent work

HowThe remote agent runs git status and git diff HEAD (capped at 512 KiB), or reads 200 transcript lines, or each subagent's tail.
SendsThe text in 32 KiB chunks over the bulk lane: the private relay if connected, otherwise public relays.
UpsideOn demand only. The pager colours diffs and shows line numbers.
DownsideLarge diffs over public relays take about 1–2 s per chunk.

Tested: ✓ diff (E10d). ◐ log and subagents use the same path but weren't run separately across devices.

Jobs routed by capability

Hownerve sync job --needs linux,aarch64 --verify '…' -- "prompt" picks the least-busy device with every capability. That device runs claude -p headless, then runs the verify command; exit 0 means verified.
SendsPrompt, needs, verify command and allowed tools. Back come progress, turns, cost and the session id.
UpsideQueues for sleeping devices. Another Claude can use it to delegate work (E16).
DownsideHeadless jobs can't ask permission, so pre-allow tools with --allow.

Tested: ✓ E13, E15, E16 (round 1, unchanged). ✗ Xcode / iOS simulator.

5. Hand-off and incremental sync NEW

Round 1 sent one tar every time: a git bundle --all (the whole history), the patch, untracked files and the whole transcript. A repeat hand-off of a busy session resent almost everything. Round 2 replaces that with a short exchange:

source (has the session) target HandoffOffer {session, repo name, root commit} ──► ◄── HandoffHave {tips its checkout already has} pack: git bundle --all --not <tips> + content-defined chunks of patch, untracked files, transcript, sidecars HandoffManifest {index of files → chunk ids} ──► ChunkData × n {only chunks it isn't known to hold} ──► ◄── ChunkWant {anything still missing} (rare) ◄── Ack "resumed in tmux nerve-xxxx" both: remember which chunks the other now holds
Git
The target names the commits it has; the bundle carries only what lies beyond them. With nothing new there is no bundle at all. The repo is identified by its root commit, so an unrelated checkout at the same path is never treated as having these commits.
Everything else
FastCDC-style content-defined chunking (gear hash; 2 KiB minimum, 8 KiB average, 32 KiB maximum), stored by SHA-256 in <sync>/chunks/. An append or an edit changes only the chunks around it.
Knowledge
<sync>/known/<peer> lists chunk ids that peer has confirmed holding. It is updated on the target's ack, and corrected if the peer later asks for a chunk again.
Integrity
Every chunk is checked against its id on arrival, so a corrupt or forged chunk is dropped. The index is itself a chunked file, so big repos don't overflow a message.
Storage
The store is pruned oldest-first above 512 MiB. A pruned chunk costs one extra request later, never correctness.
RunWhat changed since the last hand-offSentTotal size
E22 #1 (Mac, local relay)first time: new checkout694 KiB · 101/101 chunks716 KiB
E22 #2one turn + one commit16–19 KiB · 4–5/100 chunks720 KiB
E26 #1 (Pi → Mac, public relays only)first time: new checkoutall 5 chunks, 3.1 s≈ 24 KiB (small test repo)

Upside: repeat hand-offs cost roughly the size of the change, so moving a session back and forth is cheap even over public relays. Downside: the first hand-off of a big repo is still the whole history, and over public relays that is slow (paced to avoid bans). Chunks aren't compressed yet, although transcripts compress about 5×.

6. Wire format and security

EventNostr kindKept by relaysCarries
State30078 (addressable, d = nerve/2/state/<recipient>)newest only, 7-day expirythe device snapshot in §4
Messages459024 h (NIP-40 expiry)Send, Answer, SyncNow, Fetch/Blob, HandoffOffer/Have/Manifest, ChunkWant/ChunkData, JobSubmit/JobUpdate, PairRequest, Ack

Each payload is a JSON envelope {v: 2, id, from, sent_at, body}, NIP-44 v2 encrypted to exactly one device and signed by the sender. Devices on protocol v1 and v2 ignore each other rather than misreading each other.

WhoCan seeCannot see
Your paired deviceseverything above—
A public relaywhich keys talk, when, message sizes; ciphertext for up to 24 hany content
Anyone elsenothing usefulunknown keys are ignored. The one exception: a PairRequest, accepted only while an invite is open, and only with its secret.
Other users on the same machine—the mod socket is 0600 in your config directory

Trust model: a paired device can type into your sessions and approve tool calls. That is remote control by design. Treat device.key like an SSH key, and an invite code like a one-hour password.

Safety rails:

  • Only keys listed in [peers] are obeyed.
  • Message ids are de-duplicated, even across restarts.
  • Instructions expire after 5 minutes.
  • The PID is re-checked before any typing.
  • Control characters are stripped.
  • Network strings are sanitised before display.
  • Hand-off paths can't escape their directory.
  • Chunks are verified by hash.
  • Invites are single-use.

7. Transport options

SetupRound tripUpsideDownside
Public relays only (the default)0.5–0.9 sZero setup, no VPN, works from anywhereRate limits; first hand-offs of big repos are slow; relays see metadata
+ private relay on the Pi (nerve sync serve-relay, then nerve sync relay add ws://<pi-tailscale-ip>:7777)~16 msNo third party; bulk data (hand-offs, diffs) goes thereEvery device must be on your tailnet; the relay is in memory, so a restart drops queued messages (public relays cover for it)
Alternatives considered (48 surveyed in round 1)
  • iroh: fastest, but needs Rust 1.91 (nerve's minimum is 1.85) and has no store-and-forward. It is the planned bulk lane.
  • NATS / MQTT: need a reachable hub and have no end-to-end encryption.
  • Matrix: heavy SDK, Rust 1.96.
  • Tailscale + HTTP: fails the "no VPN" goal.
  • Claude Remote Control: great for phone chat, but no fleet view, hand-off, jobs or API. Use it alongside nerve.

research/sync/demo/demo.sh --check    # non-interactive; prints status and exits

Devices shows beta, its sessions, and "synced Ns ago". Both "devices" are this Mac, so its sessions are your real ones. m types into a real session, so pick a throwaway one.

research/sync/experiments/e17_mod_e2e.sh

This runs E17–E22 and prints every step, including beta's Claude screen while prompts are pending. It runs in a temp directory, loads the mod only for its own test session, and leaves nothing running.

Android with Termux

Install Termux from F-Droid or GitHub, not the stale Play Store build. Optionally add Termux:Boot so the agent starts at boot. Then either:

# build on the phone: install.sh installs rust, git, tmux, openssh from pkg first
git clone <your fork> nerve && cd nerve && ./install.sh nerve1…

or copy the prebuilt static binary (no compiler needed on the phone):

# on the Pi, once:  cargo build --release --features sync --target aarch64-unknown-linux-musl
scp pi:nerve-src/target/aarch64-unknown-linux-musl/release/nerve $PREFIX/bin/
nerve setup nerve1…

That's all you need: setup uses public relays, so the phone needs no Tailscale. Because Termux has no service manager, setup starts the agent as a detached process, takes a wake-lock, and writes ~/.termux/boot/nerve-sync for Termux:Boot. Android may still kill background apps, so exempt Termux from battery optimisation. This path is built but not yet run on a real phone.

iPhone

Install Tailscale and an SSH app (Blink Shell supports mosh, which survives sleep and network changes).
ssh you@<pi-tailscale-ip>, then nerve, then D. The Pi's service agent keeps running, and the TUI attaches to it.
Below 90 columns the view switches to tabs (Tab moves between devices). Landscape helps.

SSHing into the Mac works for nerve sync … commands. A second nerve TUI is refused while the Mac's own TUI is open, because nerve allows one instance at a time.

11. Gotchas

  • Restart sessions after setup to get the mod. Older sessions still work through tmux and hooks.
  • One agent per device key. Setup installs it as a service. Don't also run nerve sync agent by hand; the TUI detects the service and becomes a viewer.
  • macOS can't reach the Pi's LAN IP from an ad-hoc-signed binary (Local Network Privacy). Use the Tailscale address or public relays.
  • A mod is code inside Claude. Install it only from your own nerve; claude plugin validate lists every API call it makes.
  • Invite codes are passwords for an hour. Make a fresh one per device with nerve sync invite.

12. What's next

  1. A phone web app (nostr-tools, same JSON) for iPhone without SSH, plus push notifications via ntfy from the Pi.
  2. Compress chunks (zstd) for public-relay first hand-offs; iroh as the bulk lane once the minimum Rust version allows it.
