nerve cross-device sync

Can nerve sync, steer, hand off and distribute Claude Code work across your own devices over Nostr, both with and without Tailscale? Below: what was built, what was measured, and what was decided.

AnswerRequirementsMeasurementsFindingsArchitectureLandscapeDecisionsTry itLimits

Yes, and it runs. Every requirement works end to end between the real Mac and the real Pi.

Over public Nostr relays with no VPN, latency is 0.5–1 s per hop. With a private relay on the Pi over Tailscale, the same protocol runs at about 16 ms.

The transport was the easy part. The hard part was getting into a running interactive Claude session. That is solved with Claude's documented hooks plus paste injection, and each edge case was checked empirically.

Findings that shaped the design

Relays acknowledge events they then drop. nos.lol and nostr.mom returned OK for every event from a new key, then neither delivered nor stored them. Damus banned a test key within minutes. So every command gets an end-to-end ack from the receiving device, each device uses several relays, and the docs list relays verified to deliver.
Real size limits are lower than advertised. Some relays topped out at 60 KB, and one accepted only 8 KB from unknown keys. Events are split into 32 KiB chunks, and bulk data goes only through private relays when one is available.
Claude's two prompt hooks behave differently. While a PermissionRequest hook waits, the permission dialog stays on screen, so a local keypress and a remote answer race safely. A PreToolUse hook on AskUserQuestion hides the question until it returns. That is why questions only go remote in away mode. Neither hook is told when someone answers locally, so nerve watches the transcript for that.
Handoff only needs the project slug to match. Absolute paths inside the transcript didn't matter. --fork-session keeps the two devices from writing to the same history.
macOS blocks ad-hoc-signed binaries from reaching LAN IPs because of Local Network Privacy. Tailscale addresses were unaffected.

Architecture

Claude session ──PermissionRequest / PreToolUse hook──► nerve sync hook ─┐
(tmux pane / Ghostty tab)                                                 │ mailbox/
     ▲ bracketed paste                                                    ▼
     └─────────────── inject ◄──── sync agent (thread + tokio) ──── handoff / jobs
                                     │ discovery (same code as the TUI)
                                     │ NIP-44 envelopes, one per peer
                  ┌──────────────────┴────────────────────┐
           ws://pi:7777 (private,               wss://primal, wss://snort
           Tailscale, bulk lane)                (public, no VPN)
                  └──────────────────┬────────────────────┘
                                     ▼
                       other devices' agents / TUI `D` view

Two Nostr event kinds:

  • Kind 30078 (addressable): each device's latest state, one copy per recipient. Because the relay keeps only the newest, a closed laptop still shows what it was last doing.
  • Kind 4590 (stored, 24 h expiry): commands, answers, chunked data and jobs. Storage is what lets a sleeping device catch up when it wakes.

The code follows nerve's existing rules:

  • all I/O stays in the worker;
  • everything received from the network is wrapped in Sanitised;
  • Claude's data dirs come from claude_roots();
  • the PID is re-validated before typing;
  • visibility is pub(crate) only.

Landscape: why Nostr, and what else fits

OptionVerdict
Claude Code Remote ControlFirst-party, excellent for chatting and approving from a phone. It has no handoff, no fleet view and no job routing, and no public API, and it requires a claude.ai login. It complements nerve rather than replacing it.
Happy, Paseo, YepAnywhereMature remote UIs, but they own the Claude process through the Agent SDK. nerve monitors sessions it didn't start, which is why it uses hooks and paste.
CodeDeck+, ContextVMThe closest prior art on Nostr. CodeDeck+'s split of event kinds matches ours. ContextVM (MCP over Nostr) is the route to "agents drive other devices" later.
irohFastest in testing, with no setup. It needs Rust 1.91 (nerve's MSRV is 1.85) and has no store-and-forward. Planned as the bulk lane.
NATS / MQTT / ZenohMature, but every device must reach a hub, and none encrypts end to end. Without Tailscale the Pi would have to be exposed.
MatrixYou'd get a phone UI for free, but it needs Rust 1.96 and a heavy SDK.
Tailscale + HTTPThe simplest option, but it doesn't meet the no-WireGuard goal. Supported here as the fast private-relay setup.

Key decisions

All 14 decisions, with the evidence for each, are in research/sync/DECISIONS.md.

  1. Hooks, not screen scraping. Prompts are answered through hooks. Keystrokes are used only to type new instructions.
  2. Questions go remote only in away mode. Otherwise the person at the keyboard would never see them.
  3. A local answer is detected from the transcript. The hook then withdraws its remote request.
  4. Nostr, built in, behind a cargo feature. nostr-sdk's MSRV is 1.85, the same as nerve's.
  5. Every command is acknowledged end to end. A relay's OK is not proof of delivery.
  6. 32 KiB chunks. Bulk data goes over private relays only.
  7. Handoff resumes with --fork-session, inside tmux. It refuses to overwrite a checkout that has uncommitted work.
  8. Replays are blocked twice. Every message type is deduplicated across restarts, and Send has a hard 5-minute age limit.
  9. Short-lived CLI runs never execute peer commands. If a long-running agent exists, they queue to it.
  10. The Devices view selects rows by identity, not by position.
  11. MSRV 1.85 is kept by MSRV-aware lock resolution, with zero existing dependencies changed.

Try it

On one Mac, with no Pi and no internet: research/sync/demo/demo.sh starts a private relay plus a second "device" and opens the TUI (press D). Across real devices:

cargo build --release --features sync
nerve sync init --name mac --relay wss://relay.primal.net --relay wss://relay.snort.social
nerve sync pair pi npub1…            # the Pi's key; run the reverse on the Pi
nerve sync install-hooks             # start Claude with --settings <printed path>
nerve sync agent                     # on the Pi (or a systemd service)
nerve                                # press D: Devices, H: hand off the selected session

nerve sync status
nerve sync job --needs linux --allow 'Bash(python3 *)' --verify 'grep -q ok out.txt' check -- "write ok to out.txt"

Limits and next steps

  • Not built yet:
    • a phone or web client (your brief marked this "later");
    • the iroh bulk lane, which is blocked by the MSRV;
    • NIP-59 gift wrap and NIP-42 relay auth as defaults (both work, but add size and setup);
    • key rotation;
    • typing into --bg sessions.
  • Not tested:
    • Two separate networks. Both devices share a home LAN, so the no-VPN runs went through public internet relays, which is the same path a remote laptop would use.
    • The iOS simulator. This Mac has no Xcode, so routing was shown with macos/linux capabilities; ios-sim is auto-detected when Xcode is present.
  • Next:
    • a systemd/launchd agent service;
    • a PWA on nostr-tools, with ntfy push from the Pi;
    • an MCP or ContextVM server so agents can call job, send and status as tools;
    • surfacing Remote Control links in the details view.
